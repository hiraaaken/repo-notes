# Repo Notes アプリ 設計判断の理由

`design.md` は「何を作るか」を書いた仕様書。本書は「なぜそうしたのか」を書いた解説書。
ジュニアエンジニアがシニアの判断軸を獲得するための教材として読めることを意図する。

各項目は次の構造で記述する:

- **コンテキスト**: 何を決める必要があったか
- **採用**: 何を選んだか
- **なぜ**: 採用理由
- **却下案**: 検討して捨てた案と却下理由
- **シニア視点の補足**: 見落としがちな失敗パターン・運用上の罠・トレードオフの読み方

---

## 1. プラットフォーム・フレームワーク選定

### 1.1 なぜ Flutter (ネイティブや React Native ではなく)

- **コンテキスト**: Phase 1 は Android のみだが Phase 3 で Web (Svelte) も視野。
- **採用**: Flutter
- **なぜ**:
  - 1人開発 + Android 単独 + 後で Web を別実装する前提なら、ネイティブ (Kotlin/Compose) でも RN でもよい。決め手は「Dart の型・ツールチェーンが安定」「単一バイナリで開発体験が滑らか」「Riverpod と drift のエコシステムが洗練」の 3 点。
  - 個人プロジェクトでは「言語の癖と戦う時間」がそのまま実装速度に直結する。Dart は冗長だが予測可能性が高く、ハマりが少ない。
- **却下案**:
  - **Kotlin + Jetpack Compose**: 性能・OS 統合は最強だが Phase 3 の Web 対応が完全に独立実装になる。コードの再利用性は Flutter も同程度なので決定打にならない。
  - **React Native**: Web を Svelte にする時点で「同じ JS/TS で書ける」メリットが消える。RN の async/storage 周辺の地雷が個人開発には重い。
- **シニア視点の補足**:
  - フレームワーク選定は「学習コスト」だけで決めない。**保守期間中の breaking change 頻度** と **コミュニティの中央値の質** を見る。Flutter は major upgrade が比較的痛いが、移行ガイドは整っている。RN は依存ライブラリの NPM 地獄が長期保守を蝕む。
  - 「将来 iOS も出すかも」という曖昧な動機で Flutter を選ぶのは弱い理由。明確に「Web は別実装」と決めたなら Flutter を選ぶ理由は「個人の開発体験」になる。これは正当な理由だが、**チーム開発では同じ理由は通用しない**。

### 1.2 なぜ Riverpod (Provider, Bloc, GetX ではなく)

- **コンテキスト**: 状態管理ライブラリの選定。
- **採用**: Riverpod (v2.x)
- **なぜ**:
  - **コンパイル時に DI グラフが解決される** (riverpod_generator)。実行時エラーになる Provider 系の罠を避けられる。
  - **テスト容易性**: `ProviderContainer` で完全に隔離されたテストが書ける。
  - グローバル状態と画面ローカル状態を同じ抽象 (Provider) で扱える。Bloc のように「状態管理オブジェクトの種類」を覚える必要が少ない。
- **却下案**:
  - **Provider**: Riverpod の前身。Widget tree への依存が強く、テストや非同期処理で苦労する。Riverpod が後継として出ている以上、新規で選ぶ理由はない。
  - **Bloc/Cubit**: ボイラープレートが多い。チーム規模が大きい時の「全員が同じパターンで書く」強制力は価値があるが、1人開発では負債。
  - **GetX**: 機能が多すぎる (状態 + ルーティング + DI + ...) ことがアンチパターン。各レイヤーの責務が混ざり、保守性を下げる。
- **シニア視点の補足**:
  - 状態管理選定は **「どの状態をグローバルに置き、どれを画面ローカルにするか」のガイドラインを先に決める** ことの方が重要。ライブラリは手段。本アプリでは「PAT・同期状態・タグマスタ」がグローバル、「メモ入力フォーム・現在のフィルタ」が画面ローカル、と切り分ける。
  - Riverpod の `family` は強力だが乱用すると「Provider の組み合わせ爆発」を招く。最初は使わず、必要が出てから導入する。

### 1.3 なぜ go_router

- **コンテキスト**: ルーティング。
- **採用**: go_router (公式推奨)
- **なぜ**:
  - URL ベースの宣言的ルーティング。Phase 3 の Web 版 (Svelte) と URL 設計の思想を揃えやすい。
  - Deep link / アプリリンクの実装が素直。
  - Riverpod との相性が良い (公式に integration パターンがある)。
- **却下案**:
  - **Navigator 2.0 直叩き**: 学習コストと記述量で go_router の存在意義が成立。
  - **auto_route**: コード生成が強力だが、go_router で十分な要件で重い選択。
- **シニア視点の補足**:
  - Phase 1 はタブ 3 つ + モーダルだけなので、ルーティングの恩恵は限定的。とはいえ **後から差し替えるコストが大きい部分は最初から正解を選ぶ** のが鉄則。
  - URL 設計を `/notes/:path` のような形にしておくと、Phase 2 の wikilink タップ遷移と Phase 3 の Web 版で URL を共有できる。**今は使わなくても URL を設計するだけはやっておく** と将来の自分が助かる。

### 1.4 なぜ drift (sqflite, hive, isar ではなく)

- **コンテキスト**: ローカル DB。
- **採用**: drift (旧 moor)
- **なぜ**:
  - **型安全な SQL** (コード生成)。SQLite の力 (JOIN, 集計, FTS5) をフルに使える。
  - スキーママイグレーションが書きやすい (バージョン番号 + 変更スクリプト)。
  - リアクティブクエリ (`watch`) が Riverpod の `StreamProvider` と素直に繋がる。
- **却下案**:
  - **sqflite**: 生 SQL を文字列で書く。型安全性ゼロ。drift の登場で選ぶ理由がなくなった。
  - **hive**: NoSQL (key-value)。M:N リレーション (note_tags) を表現するには不向き。タグ別ノート一覧を高速に取りたいので JOIN が使える drift が勝る。
  - **isar**: 高速だが M:N の表現が独特で、SQL の知識が転用しづらい。エコシステムが drift より小さい。
- **シニア視点の補足**:
  - **「速さ」より「クエリ表現力」を優先する** のが本アプリの正解。100〜1000 ノート規模では SQLite で十分速い。「タグ別 + kind フィルタ + 日付ソート + 全文検索」という組み合わせクエリの将来性で drift を選んだ。
  - drift の落とし穴: コード生成の build_runner が遅い。watch モード (`flutter pub run build_runner watch`) を最初から使う習慣をつけること。

### 1.5 なぜ markdown_widget (flutter_markdown ではなく)

- **コンテキスト**: Markdown レンダリング。
- **採用**: markdown_widget
- **なぜ**:
  - **`flutter_markdown` は 2024 年に discontinue された** (公式メンテナンス停止)。新規プロジェクトで採用するのは技術負債を背負う行為。
  - markdown_widget は wikilink (`[[link]]`) のような独自記法を拡張しやすい。Zettelkasten 用途でこの拡張性は将来効く。
- **却下案**:
  - **flutter_markdown**: 既にメンテされていない。
  - **gpt_markdown**: GitHub-flavored Markdown のサポートが厚いが、wikilink 拡張が markdown_widget より弱い。
  - **自前 Markdown パーサ**: コストが見合わない。
- **シニア視点の補足**:
  - **「公式 = 最善」ではない**。Flutter team の official package も discontinue される。**選定時に必ず最終コミット日と issue tracker の活発度を見る**。
  - パッケージの寿命は「使っているプロジェクトの数」だけでは測れない。「メンテナの動機が続くか」を見る。個人 OSS は飽きる、企業 OSS は事業方針で打ち切られる。**自分のアプリの寿命より長く生き残るかを賭ける気持ちで選ぶ**。

### 1.6 なぜ workmanager

- **コンテキスト**: バックグラウンドで日次 fetch を走らせる。
- **採用**: workmanager (Android の WorkManager をラップ)
- **なぜ**:
  - Android の **Doze mode と App Standby に正しく対応する** には WorkManager 経由が事実上唯一の選択肢。AlarmManager 直叩きは省電力モードで発火しない。
  - 制約 (WiFi 必須・充電中など) を OS に委譲できる。
- **却下案**:
  - **AlarmManager**: Doze mode で発火しない可能性。再試行戦略を自前で書く必要があり、再発明。
  - **Foreground Service 常駐**: バッテリー消費とユーザー体験 (常時通知) が悪い。
- **シニア視点の補足**:
  - **「7:00 に発火させたい」≠「7:00 ジャストに発火する」**。WorkManager は OS の都合で 7:00〜10:00 のどこかで発火する。要件として「朝のうちに 1 回」を許容範囲にすることが、設計と実装の両方で必須。
  - バッテリー消費はユーザーがすぐ気づく。WiFi 制約 (`UNMETERED`) を必ずつけて、モバイル回線で tar.gz をダウンロードしないように。

### 1.7 なぜ flutter_secure_storage

- **コンテキスト**: PAT (GitHub fine-grained Personal Access Token) の保管。
- **採用**: flutter_secure_storage
- **なぜ**:
  - Android では Keystore、iOS では Keychain を抽象化する。**OS が保証するセキュリティ境界の中に PAT を入れる** のが本筋。
  - SharedPreferences に平文保存は論外 (root 端末や ADB バックアップで漏れる)。
- **却下案**: なし。これは「他に選択肢がない」類の選定。
- **シニア視点の補足**:
  - **PAT は「漏れたら全権を奪われる credential」**。fine-grained で `hiraaaken/base` の Contents R/W に絞っているのは正解。これにより漏洩時の被害が「リポジトリの書き換え・削除」に限定される (アカウント乗っ取りは起きない)。
  - **「個人開発だから OS Keystore で十分」と判断したことを docs に書いておく**。HSM を使う、サーバ経由で OAuth する、等の上位策が存在することを認識した上で「個人スコープではここで十分」と判断した、という記録が後で別アプリ作る時の判断資料になる。

### 1.8 なぜ dio (http ではなく)

- **コンテキスト**: HTTP クライアント。
- **採用**: dio
- **なぜ**:
  - **interceptor で PAT を全リクエストに自動付与** できる。`Authorization: Bearer ...` を毎回書く必要がない = 書き忘れによる事故を防げる。
  - リトライ戦略・タイムアウト・キャンセルが標準で揃う。
- **却下案**:
  - **package:http**: 公式だが機能が最小限。Interceptor を自前で書くと再発明。
- **シニア視点の補足**:
  - HTTP クライアント選定で **本当に効くのは interceptor の有無**。認証・ロギング・エラーハンドリング・リトライを一箇所に閉じ込められるかが、5 年後の保守性を左右する。

## 2. データモデル設計

### 2.1 なぜ `kind` と `genre` を別軸にしたか

- **コンテキスト**: ノートの種別をどう表現するか。最初は「ジャンル → そのジャンルのタグ」の階層型を検討した。
- **採用**: `kind` (リポジトリ内のノート種別) と `genre` (メモを書いた時点の意図) を直交させる。`tags` (トピック) も独立。
- **なぜ**:
  - **概念の軸が違うものを同じ階層に入れると、後で必ず歪む**。`literature` と `idea` を同じ enum に並べると、「読書ノートだけど思いつきも書いた」が表現できなくなる。
  - 階層型 (genre が tags を内包) はメモ入力時に「ジャンル選び → タグ候補絞り込み」の 2 段階クリックが必要になり、UX シナリオを描いた時点で煩雑さが見えた。
  - 直交させると `genre=reading + tags=[flutter, mobile]` のように、軸が独立に増減できる。
- **却下案**:
  - **階層型**: 上記の通り。
  - **`genre` を tags の中に含める** (`tags=[idea, flutter]`): タグの中にメタ的なものと内容的なものが混ざり、検索・フィルタの仕様が複雑になる。
- **シニア視点の補足**:
  - データモデル設計の鉄則: **「正規化された直交軸」を優先**。1 つの列に複数の意味を持たせると、後で SELECT 時に必ず複雑な WHERE が要るようになる。
  - とはいえ「軸を増やしすぎる」も罪。本アプリは `kind` / `genre` / `tags` の 3 軸 + 時系列 (`created`) で止めている。これ以上増やすときは既存軸の役割が満たせていないか先に確認する。

### 2.2 なぜ `genre: research` を `investigate` にリネームしたか

- **コンテキスト**: メモ frontmatter の genre と notes.kind の両方に `research` があり、意味が違った (前者は「これから調べてほしい」、後者は「調査結果ノート」)。
- **採用**: メモ genre 側を `investigate` にリネーム。
- **なぜ**:
  - **同じ語彙が文脈で違う意味を持つと、コードレビュー・障害対応・新人説明の全てで毎回認知コストがかかる**。
  - リネーム対象 2 つのうち memo genre 側が「新設」なのでコストが低い。notes.kind 側は既存リポジトリの命名 (`research/*.md` ディレクトリ) と一致しており、変更の波及が広い。
- **却下案**:
  - **そのまま `research` で両方使う**: 現時点では支障がなくても、3 年後に新メンバーが入ってきた時に必ず「どっちの research?」と聞かれる。
  - **`notes.kind` 側を `inquiry` にリネーム**: 既存リポジトリのディレクトリ名と整合しなくなる。
- **シニア視点の補足**:
  - **「語彙の衝突」は最初の 5 分で潰せ、放置すると永遠に残る**。コードベースの中で最も改名コストが低いのは「導入直前」。リリース後は呼び出し箇所・docs・ユーザーの記憶の全てに影響する。
  - 命名の代替案を出すときは **「どちらがより一般的な英語か」よりも「どちらが既存資産との整合性が高いか」を優先**。一般語彙は後で wiki を引けば分かるが、既存資産の命名変更はコストが青天井。

### 2.3 なぜタグを M:N 中間テーブルで正規化したか (JSON 配列で持たないか)

- **コンテキスト**: タグの保存方法。
- **採用**: `note_tags` 中間テーブル + `tags` マスタ + `tags.count` キャッシュ列。
- **なぜ**:
  - **「タグ別ノート一覧」と「タグ頻度ランキング」を高速に取りたい**。JSON 配列で持つとフルスキャン + JSON パースが必要になる。
  - タグの正規化 (大小文字保持・空白 trim) を 1 箇所に閉じ込められる。
- **却下案**:
  - **`tags` 列に JSON 配列**: クエリが書きにくい。SQLite の `json_each` で展開できるが、毎回パースする実行時コストと、SQL の見通しが悪化する。
  - **カンマ区切り文字列 (`flutter,mobile`)**: 部分一致 LIKE が必要になり、`mobi` でも誤マッチする等の事故を起こす。
- **シニア視点の補足**:
  - 正規化 vs 非正規化の判断は **「クエリパターン」を先に並べてから決める**。本アプリは「タグ集計」と「タグ別フィルタ」が頻出 → 正規化が正解。逆に「常に全件 JOIN で読み込む」用途なら非正規化の方が速い。
  - `tags.count` のような **キャッシュ列** は更新タイミングを明確にしないと不整合の温床。本アプリでは「同期完了時に再計算」と決めている。これがないと「タグマスタは正しいのに count だけずれる」が発生する。

### 2.4 なぜ `notes.raw` 列に本文をフル保存するか

- **コンテキスト**: ノート本文をどこに置くか。
- **採用**: `notes.raw` に frontmatter 含めた全文を 1 列で保存。
- **なぜ**:
  - **再パースのコスト < ストレージのコスト** (~500KB 程度なら問題にならない)。
  - frontmatter 改変時に row 単位で書き直せる (列を分けると複数列の更新になり、トランザクション境界の管理が増える)。
  - 表示時に `gray_matter` 相当で frontmatter を剥がす単純な責務分離。
- **却下案**:
  - **frontmatter と本文を別列**: 一見正規化されているが、実際は frontmatter のフィールドを個別列に分解する (kind, created, tags, ...) ので、本文を分ける意味が薄い。
  - **本文をファイルシステムに置く**: SQLite トランザクションの外に出ると整合性管理が爆発する。
- **シニア視点の補足**:
  - **「正規化教 vs 非正規化教」を相対化する** のがシニアの仕事。本アプリは「frontmatter のフィールドは個別列に展開、ただし本文と raw は両方保持」という中庸を取った。raw を残すのは「将来 frontmatter のスキーマが変わった時、再パースで吸収できる保険」のため。
  - データサイズの見積もりは **「現在の規模」だけでなく「想定上限の 10 倍」で計算する**。1000 ノート × 500KB = 500MB は SQLite では問題ないが、5000 ノート想定なら lazy load を考える。Phase 1 では 100 ノートなので raw 保持で何の問題もない。

## 3. 同期戦略

### 3.1 なぜ tarball + delete-insert (差分同期しない)

- **コンテキスト**: ローカル DB を GitHub リポジトリと同期する方法。
- **採用**: `GET /tarball/main` で全ファイル取得 → ローカル `notes` 系テーブルを delete → insert。
- **なぜ**:
  - **「コードが単純で整合性が高い」が個人開発における最大の正義**。差分同期は「rename をどう検知するか」「削除をどう検知するか」「途中エラー時の状態」を全部設計する必要がある。
  - 100 ファイル ~200KB なら tarball 1 リクエストで済む。差分同期は per-file リクエストで N+1 問題を起こす。
  - WiFi 前提 + 朝 1 回の発火なので、データ量・通信量とも問題なし。
- **却下案**:
  - **per-file 差分同期 (`GET /repos/.../contents/{path}` を変更ファイルだけ)**: 個別 SHA 比較が必要。`GET /commits` で変更ファイル一覧を取り、それぞれ取得する。リクエスト数が多く、API rate limit を消費する。
  - **GraphQL API で 1 リクエストに合成**: 効果は同じだが GraphQL の習得コストが、得られる効率に見合わない (この規模では)。
- **シニア視点の補足**:
  - **「最適化は規模が来てから」を守る** のが個人開発の鉄則。1000 ファイル超になったら差分同期に切り替える、という growth path を docs に書いておけば十分。最初から差分同期を組むと、複雑さの利息で完成しない。
  - delete-insert の落とし穴は **「途中で失敗したらデータが消える」**。Drift の **トランザクション内で delete + insert** することで「全部成功するか、全部巻き戻るか」を保証する。トランザクション境界を間違えると一瞬空っぽの DB をユーザーに見せることになる。

### 3.2 なぜ `memo_queue` を delete-insert から分離するか

- **コンテキスト**: ローカル DB の同期戦略。
- **採用**: `notes` / `note_tags` / `tags` は delete-insert、`memo_queue` は分離。
- **なぜ**:
  - **`memo_queue` は「リモートに存在しない・ローカルにしかないデータ」**。delete-insert すると消える = ユーザーのメモが失われる。これは絶対にやってはいけない。
  - データの「ソース・オブ・トゥルース」が違う: notes 系は GitHub リポジトリが真、memo_queue はローカル端末が真。
- **却下案**: なし (これは選択肢のない正解)。
- **シニア視点の補足**:
  - **テーブルごとに「真の所在」を明示する** のは、データ層を設計するときの最重要事項。本アプリは:
    - notes 系: GitHub 真 (キャッシュ)
    - memo_queue: ローカル端末真 (送信キュー)
    - sync_state: ローカル端末真 (メタ)
    - tags マスタ: 派生 (notes 真から計算)
  - これを明示しておくと **「テーブル X を全削除していいか?」の判断が一瞬で出る**。真がローカルなら削除は破壊的、真がリモートならいつでも再構築可能。

### 3.3 なぜ `daily.md` を append-only stream として扱うか

- **コンテキスト**: アプリが `daily.md` に書き込む方法。
- **採用**: 末尾追記しか行わない。編集や削除はリポジトリ側 (人間 or バッチ) の責務。
- **なぜ**:
  - **append-only は競合解決を「直列化」に縮約できる** 最強パターン。SHA 衝突しても「最新を取り直して再 append」だけで済む。マージは不要。
  - 「アプリが過去メモを編集する」を許すと、`/schedule` バッチがメモを別ファイルに移動した後にアプリが古い場所を編集する、というレース条件が出る。append-only ならこの問題は構造的に発生しない。
- **却下案**:
  - **アプリが任意位置を編集**: 競合解決が指数的に複雑になる。3-way merge を Markdown でやるのは現実的でない。
  - **アプリが daily.md を完全置換**: バッチが書いた変更を上書きする可能性。
- **シニア視点の補足**:
  - **「データの書き込み権限を物理的に制限する」設計パターン** をマスターしておくと、分散システムの 9 割が単純化する。append-only ログ・WORM ストレージ・event sourcing は全部この発想。
  - 制限を docs に書くだけでなく、コードでも防ぐ (例: PUT 時に必ず「既存内容 + 新メモ」の組み立てしか経由しない関数を 1 つ用意し、編集系のメソッドを作らない)。**「やってはいけないことを書けないコードベース」が事故を防ぐ**。

### 3.4 なぜ `dedup_key` を導入するか

- **コンテキスト**: append commit の冪等性確保。
- **採用**: `SHA-256(created_at_iso + "\n" + body)` を `memo_queue.dedup_key` に保存。append 前後でリモート最新 N 件と照合して重複を弾く。
- **なぜ**:
  - **「commit 成功 → ローカル削除前に kill」のレース条件** を防ぐ。リモートには既に append 済みなのにローカル queue に残っているケースで、再 flush 時に重複 append しないため。
  - 「ネットワークタイムアウトで commit 結果が不明」のケースも、再試行しても重複しないので安心して retry できる (= **at-most-once でなく at-least-once + 冪等性で正解にする** のがメッセージング設計の常套手段)。
- **却下案**:
  - **冪等性を諦める**: 重複 append を許容することになり、ユーザーが daily.md を読んだ時に同じメモが 2 回出る。これは UX として致命的。
  - **commit message に UUID を入れて GitHub の commit history で照合**: API 呼び出しが 1 回増える上、commit 履歴を真の所在として扱うことになり、`daily.md` の中身との一貫性が崩れる可能性。
- **シニア視点の補足**:
  - **冪等性の鍵は「同じ操作を 2 回やっても 1 回と同じ結果になる」**。dedup_key はその鍵そのもの。
  - dedup_key の計算式に何を入れるかは **慎重に**。本アプリでは `created_at + body` のみ。tags や genre を含めると「タグ修正後再送」のケースで別キーになり、重複 append の脆弱性ができる。
  - SHA-256 の衝突確率は実用上ゼロだが、ローカルで複数の同時刻同本文を意図的に作るケース (極稀) は残る。Phase 1 では諦め、必要なら Phase 2 で `+ random nonce` を追加する。

### 3.5 なぜ B + D の二段構え自動 fetch か

- **コンテキスト**: 自動 fetch の戦略。
- **採用**: B (WorkManager 日次 7:00) + D (起動時、最終 fetch から 6h 以上経過時) の両方。
- **なぜ**:
  - **B 単独**: アプリを開かない日でも fetch されるが、OS が WorkManager を 7:00 に発火する保証はなく (Doze など)、最悪 1 日飛ぶことがある。
  - **D 単独**: アプリを開いた時しか fetch されない。週末に何日も開かないと差分が大きくなる。
  - **B + D**: 朝アプリを開けば D で即時取得、開かなくても B が朝のうちに走る。両方発火しても短絡判定 (`tree.sha` 比較) で 2 回目は no-op。
- **却下案**:
  - **手動 Pull-to-Refresh のみ**: ユーザーがリフレッシュを忘れる。「メモタブを開いた時に最新でない」体験。
  - **アプリ起動時の毎回 fetch**: アプリを頻繁に開く日に無駄な fetch が増える。
- **シニア視点の補足**:
  - **「OS のスケジューリングは保証されない」を前提に冗長化する** のが Mobile の鉄則。iOS の Background Fetch は更にひどい。「絶対に走ってほしいタイミング」は複数のトリガーでカバーする。
  - ただし冗長化は **競合 (race condition) を生む**。本アプリは単一 mutex で直列化することで両立している。冗長化と排他制御は対で考える。

### 3.6 なぜ単一 mutex で同期処理を直列化するか

- **コンテキスト**: B / D / 手動リフレッシュ / メモ flush の同時実行制御。
- **採用**: プロセス内で 1 つの `Lock` を全員が共有。後発は try-lock で no-op skip。
- **なぜ**:
  - delete-insert + 別の delete-insert が並走すると、**トランザクション間で行が行方不明になる**可能性がある (SQLite はテーブルレベルロックだが、アプリレベルの整合性は保証されない)。
  - メモ append と fetch が同時に走ると、「fetch がリモートを読んだ直後に append が同じ場所に commit、fetch が古いスナップショットで delete-insert」という時系列で、最新メモがローカルから消えるバグを起こす。
  - 1 つの mutex で全員直列化すれば、上記が構造的に発生しない。
- **却下案**:
  - **テーブル別 lock**: 細粒度で性能は上がるが、本アプリの規模では不要。
  - **lock なし (= 楽観的並行制御)**: バグの温床。1 人が「気合で気をつける」ような設計は失敗する。
- **シニア視点の補足**:
  - **「正しさ ≫ 性能」を最初に確保し、性能が問題になってから細粒度化する**。性能の問題は計測すれば分かるが、レース条件のバグは「再現しないバグ」になり、最も診断コストが高い。
  - mutex 設計は **「lock を取る順序」と「lock を持つ最大時間」を明示する**。本アプリでは「lock 取得 → 全 IO 完了 → lock 解放」という単純パターン。長時間 lock を保持する場合は lock-free な前処理 (キャンセル可能) を分離するパターンが要るが、Phase 1 では不要。

## 4. UI / UX

### 4.1 なぜ `daily.md` を Markdown レンダリングしないか

- **コンテキスト**: メモタブの表示方法。
- **採用**: Markdown としてレンダリングせず、各メモをカード分割して表示。
- **なぜ**:
  - **`daily.md` は構造化されたメモストリーム** であり、長文の Markdown 文書ではない。
  - カード形式 (時刻 + タグ chips + 本文) で「いつ何を書いたか」が一覧できる UX が Zettelkasten + Quick Memo の用途に合う。
  - Google Keep / Apple Notes と認知パターンが合うので学習コストゼロ。
- **却下案**:
  - **Markdown レンダリング**: 1 ファイルが長大な Markdown として表示され、メモごとの境界が視覚的に分かりにくい。
- **シニア視点の補足**:
  - **「ファイルの物理形式」と「UI 表現」を分けて考える**。同じ Markdown ファイルが、メモタブではカード、ノート詳細では Markdown レンダリング、と用途で表現を変える。データはひとつ、ビューは複数、が UX 設計の基本。

### 4.2 なぜ Phase 1 でエラー可視化 (設定画面に sync 状態) を入れるか

- **コンテキスト**: 当初は「Phase 2 でエラー通知」だった。
- **採用**: Phase 1 で **設定画面に「最終 sync 時刻 / 結果 / エラー文」を必ず表示**。プッシュ通知は Phase 2。
- **なぜ**:
  - **PAT の有効期限は最大 1 年**。期限切れで sync が失敗し続けても、ユーザーが気づかない期間が長すぎる。
  - 表示するだけなら実装コストが極小 (sync_state テーブルに `last_error` 列を 1 つ足すだけ)。
  - サイレント失敗は **「最も発見が遅れるバグ」**。プッシュ通知より「設定画面で確認できる」が優先。
- **却下案**:
  - **Phase 2 に持ち越し**: 期限切れ後にメモが何日も送信されない事故が発生する。データ損失ではないが、ユーザーの信頼を失う。
- **シニア視点の補足**:
  - **「サイレント失敗を許してはいけない」はシニアエンジニアの絶対原則**。エラーは必ずどこかに観測点を置く: 通知・ダッシュボード・ログ・設定画面のどれか。
  - 「実装コストが極小なのに価値が大きい」機能は **必ず Phase 1 に入れる**。Phase 切りはコストとリスクのバランスで決めるべきで、「機能を後回し」は時に「リスクの先送り」になる。

### 4.3 なぜ Phase 1 で wikilink を「素通し表示」にするか

- **コンテキスト**: `[[link]]` 記法の扱い。
- **採用**: Phase 1 は文字列としてそのまま表示 (リンク化しない)。Phase 2 でタップ遷移を実装。
- **なぜ**:
  - wikilink のリンク解決は「リンク先が存在するかの検証 + クリック時のルーティング + 削除済みリンクの扱い」が必要で、Phase 1 で組むには副作用が大きい。
  - 素通し表示なら見えるので **「リンクがあるノートだ」という認識はできる**。タップで遷移できないだけ。
  - 「中途半端にタップ可能」より「意図的に Phase 1 では非対応」と明示する方がユーザー体験として一貫する。
- **却下案**:
  - **Phase 1 から実装**: スコープ膨張。
  - **削除して非表示**: 元データを変えるのは論外。
- **シニア視点の補足**:
  - **「Phase 切り」は機能ごとのスコープではなく、機能内の "レベル"** で切ると上手くいく。wikilink は「素通し → 表示のみ → タップ遷移 → backlink 表示」と 4 段階に切れる。Phase 1 は「素通し」だけ。
  - 「最低限の表示」を Phase 1 に入れることで、ユーザーは Zettelkasten の構造を端末で目視できるようになる。完全な相互遷移はなくても、認知の支援にはなる。

## 5. データフォーマット

### 5.1 なぜ frontmatter (YAML) フォーマットか

- **コンテキスト**: メモのメタデータをどう書くか。
- **採用**: Markdown frontmatter (YAML)。
- **なぜ**:
  - **既存の `literature/*.md` 等のノートと書式が統一できる**。同じパーサで両方扱える。
  - エディタ (Obsidian, VS Code 等) で開いたときに普通のノートとして読める。
  - 機械可読 (YAML パーサが標準的) かつ人間可読。
- **却下案**:
  - **JSON**: 機械可読だが人間が手で書きにくい (引用符・カンマ)。Markdown ノートとして見たときに違和感。
  - **TOML**: YAML より厳密だが、Markdown 界隈の慣習が YAML。
- **シニア視点の補足**:
  - **データフォーマット選定は「想定される編集者」で決める**。本アプリは「アプリが書く」+「人間がエディタで編集することもある」のハイブリッド。両方に優しいのが YAML frontmatter。
  - YAML の罠: インデント・引用符・null 値の扱いがパーサ実装によって微妙に違う。**自前パーサは絶対に書かず**、`yaml` パッケージのような枯れた実装を使う。

### 5.2 なぜ `created` を UTC 固定か

- **コンテキスト**: メモ作成時刻の保存形式。
- **採用**: ISO 8601 UTC (`YYYY-MM-DDTHH:MM:SSZ`)。
- **なぜ**:
  - **「保存は UTC、表示はローカル」は時刻処理の絶対原則**。タイムゾーン情報を付けたまま保存すると、海外旅行先でメモ → 帰国 → JST で見ると順序が狂うバグを生む。
  - UTC で比較すれば順序が一意に決まる。並び替え・dedup_key の計算が単純。
- **却下案**:
  - **JST 固定**: 日本国内なら動くが、移動中にメモを書いた瞬間に破綻する。
  - **タイムゾーンつき (`+09:00`)**: 比較の際に変換が要る。dedup_key の文字列が同じ瞬間でも違う表現になる可能性がある。
- **シニア視点の補足**:
  - **時刻処理のバグは半年後に出る**。サマータイムを持つ国を含む、年末年始 (タイムゾーン跨ぎ)、複数端末で同期、などの稀な条件で発火する。Phase 1 から UTC 固定にしておけば全部回避できる。
  - UI 表示も「カードリストの並び順」と「カードに表示する時刻文字列」は分離する。並び順は UTC で比較、表示はローカル文字列にフォーマット。

### 5.3 なぜ `genre` を 3 値固定の enum にしたか

- **コンテキスト**: メモジャンルの定義。
- **採用**: `idea` / `reading` / `investigate` の 3 値固定。
- **なぜ**:
  - **「自由文字列」を使うと、`/schedule` バッチ側が無限の値に対応する必要があり、結合度が上がる**。
  - メモを書く時の認知コストを最小化する (3 択なら迷わない)。
  - 増やしたくなったら docs と enum に追加するだけ。
- **却下案**:
  - **自由文字列**: タイポと表記揺れで分類が壊れる (`idea` / `Idea` / `アイデア`)。
  - **タグの一部として扱う** (`tags=[idea, ...]`): 5.1 で検討済み (軸が混ざる)。
- **シニア視点の補足**:
  - **enum vs 自由文字列の判断: 「想定される値の集合が 1 年で何回変わるか」で決める**。
    - 月単位で変わる → 自由文字列 + 履歴管理
    - 年単位で変わる → enum
    - ほぼ変わらない → enum + コードで強制
  - 本アプリの genre は「メモ作者の意図ヒント」で、意味カテゴリは安定している → enum が正解。

### 5.4 なぜ「行頭 `---` のみ禁止」か (本文中の `---` 全面禁止ではなく)

- **コンテキスト**: パーサ仕様の制約。
- **採用**: 行頭 (前後空白なしの単独行) の `---` のみ禁止。インラインの `---` (例: `これは---ダッシュ`) は許可。
- **なぜ**:
  - **state machine が見るのは「行頭 ^---$」だけ**。インラインの `---` をパースで誤認することはない。
  - 全面禁止にすると、ユーザーが文章中で「---」を使えなくなり (CSS の border-style や、ハイフンを 3 つ並べる装飾)、UX が損なわれる。
  - 制約は **必要最小限** にする。
- **却下案**:
  - **全面禁止**: 過剰制約。
  - **エスケープ記法導入**: パーサが複雑になる。
- **シニア視点の補足**:
  - **「最小制約の原則」を意識する**。仕様の制約は「これがあると実装が壊れる」最小限に絞る。「念のため禁止」を増やすと、ユーザーは制約を覚えきれず、結局守られない。
  - 制約を docs に書く時は **「なぜその制約が必要か」を 1 行で添える**。本アプリでは「メモ境界のパースを単純化するため」と書いてある。これがないと将来「この制約消せるんじゃないか」と誰かが消して、パーサが壊れる。

### 5.5 なぜタグの大小文字を保持するか (小文字化しないか)

- **コンテキスト**: タグ正規化のルール。
- **採用**: 大小文字は保持。前後 trim と内部空白禁止のみ正規化。
- **なぜ**:
  - **ユーザーが書いた表記を尊重する**。`Flutter` (固有名詞) と `flutter` (一般動詞) を区別したい人がいる可能性。
  - 日本語タグには大小文字の概念がないので、英語タグだけのために挙動を変えると一貫性が崩れる。
  - 検索が「完全一致」ベースなら、大小文字を保持しても問題ない。
- **却下案**:
  - **全部小文字化**: `Flutter` と `flutter` が dedupe される。意図せぬマージ。
- **シニア視点の補足**:
  - **正規化は「データを失う操作」**。可逆な正規化 (trim) と不可逆な正規化 (lowercase) を区別する。不可逆な正規化は「ユーザーの意図」を壊す可能性があるので、要件として強く必要なときだけ採用する。
  - 検索時のあいまい一致 (case-insensitive search) は **検索クエリ側で `LOWER()` を使えばよい**。データ側を小文字化する必要はない。

## 6. 認証・セキュリティ

### 6.1 なぜ fine-grained PAT (classic PAT や OAuth ではなく)

- **コンテキスト**: GitHub への認証手段。
- **採用**: fine-grained PAT。`hiraaaken/base` の Contents R/W のみ許可。
- **なぜ**:
  - **権限を最小化できる**。classic PAT は repo スコープ全体になり、漏洩時の被害が大きい。
  - OAuth Apps はサーバ (callback URL) が必要で、個人開発のオーバーヘッドが見合わない。
  - fine-grained PAT は最大 1 年で expire するので、定期的に rotate される (= 漏洩時の暴露期間が限定される)。
- **却下案**:
  - **classic PAT**: 権限が広すぎる。
  - **OAuth App**: 本人 1 人しか使わないアプリにバックエンドは過剰。
  - **GitHub App**: 本人 1 人 + 1 リポジトリの規模では設定コストが見合わない。
- **シニア視点の補足**:
  - **認証手段の選定は「権限の粒度」と「漏洩時の被害範囲」で決める**。「自分しか使わないから何でもいい」は危険な発想。端末紛失・ADB バックアップ漏れ・誤コミットなど、漏洩経路は意外と多い。
  - PAT 期限切れ運用を docs に書く: **「期限の 1 ヶ月前にリマインダーをカレンダーに入れる」** ような人間プロセスをセットで設計する。技術だけでは運用は回らない。

## 7. Phase 切り

### 7.1 なぜ FTS5 全文検索を Phase 2 に回すか

- **コンテキスト**: 検索機能の Phase。
- **採用**: Phase 1 はタイトル + タグの完全一致 (or LIKE)、Phase 2 で FTS5。
- **なぜ**:
  - **100 ノート規模ではタイトル + タグだけでも十分発見できる**。
  - FTS5 はトリガで notes 更新時に index も更新する仕組みが要り、delete-insert 同期との整合 (index も全部消して全部入れる) が増える。
  - Phase 1 を最小スコープで切ることで、MVP リリースまでの時間を短縮する。
- **却下案**:
  - **Phase 1 から FTS5**: スコープ膨張。
  - **検索なし**: 100 ノートでも「あのとき書いたメモ」を探せないと不便。
- **シニア視点の補足**:
  - **Phase 切りは「ユーザーが我慢できる UX 劣化レベル」で決める**。Phase 1 で「検索できないが手で探せる」は許容範囲、「メモを書けない」は論外。「メモを書けてもサイレント失敗する」も論外 (4.2 で Phase 1 に上げた理由)。

### 7.2 なぜプッシュ通知を Phase 2 に回すか

- **コンテキスト**: 同期エラーの通知方法。
- **採用**: Phase 1 は設定画面の表示のみ、Phase 2 でプッシュ通知。
- **なぜ**:
  - プッシュ通知の実装は FCM 統合・通知権限・通知タップ時の deep link が必要で、スコープが大きい。
  - 設定画面の表示でサイレント失敗の最悪ケース (PAT 期限切れに長期間気づかない) は防げる。
  - 「プッシュで起こされる」体験は本アプリの中心 UX ではないので、後回しが妥当。
- **却下案**:
  - **Phase 1 から実装**: スコープ膨張。
- **シニア視点の補足**:
  - **「最悪ケースを防ぐコスト」と「最良の UX を実現するコスト」を区別する**。前者は Phase 1 に必須、後者は Phase 2 以降で OK。本アプリでは「サイレント失敗の防止 = 最悪ケース防止」を Phase 1、「プッシュ通知 = 最良 UX」を Phase 2 に切り分けた。

## 8. 設計判断のメタパターン (シニアの思考軸)

ここまでの判断に共通する「シニアエンジニアが意識する判断軸」を抽出する。これらはどのプロジェクトでも転用可能。

1. **直交軸を保つ** (2.1, 2.3): 概念の軸が違うものを混ぜない。混ぜると 1 列に 2 つの意味が乗り、SELECT の WHERE が肥大する。
2. **真の所在を明示する** (3.2): テーブル・データソースごとに「真はどこか」を docs に書く。これがないと「全削除していいか?」の判断ができない。
3. **冪等性を確保する** (3.4): at-least-once + 冪等で運用すると、ネットワークの信頼性に依存しない設計になる。
4. **冗長化と排他制御は対** (3.5, 3.6): 信頼性のために冗長化したら、必ず競合制御をセットで設計する。
5. **append-only は競合解決の最強パターン** (3.3): 物理的に書ける場所を制限することで、3-way merge を回避する。
6. **書ける場所を物理的に制限する** (3.3): 「やってはいけないこと」を書けないコードベースが事故を防ぐ。
7. **正しさ ≫ 性能** (3.6): 性能問題は計測で見つかる。レース条件のバグは「再現しない」ので最も高コスト。
8. **サイレント失敗を許さない** (4.2): エラーは必ずどこかに観測点を置く。
9. **Phase 切りは "機能ごと" でなく "機能内のレベル" で** (4.3): 1 機能を「最小 → 改良」と段階に切ると、各 Phase が小さく収まる。
10. **保存は UTC、表示はローカル** (5.2): 時刻のバグは半年後に出る。最初から UTC で固定。
11. **enum vs 自由文字列は変化頻度で決める** (5.3): 月単位で変わるなら自由文字列、年単位なら enum。
12. **正規化は不可逆な操作** (5.5): lowercase のような不可逆正規化は、要件として強く必要なときだけ。
13. **最小制約の原則** (5.4): 制約は実装が壊れる最小限に。「念のため禁止」は守られない。
14. **権限の最小化** (6.1): 認証手段は「漏洩時の被害範囲」で決める。
15. **「最悪ケース防止」と「最良 UX」を区別する** (7.2): 前者は MVP 必須、後者は後回しで OK。
16. **最適化は規模が来てから** (3.1): growth path を docs に書いておけば、最初から複雑化しなくてよい。
17. **「公式 = 最善」ではない** (1.5): メンテナンス停止のリスクは公式パッケージにもある。最終コミット日と issue tracker を見る。
18. **データフォーマットは想定される編集者で決める** (5.1): 機械が書く / 人間が書く / 両方、で正解が変わる。

これらは互いに独立ではなく、**「正しさを構造で担保する」** という 1 つの哲学のバリエーション。シニアエンジニアの仕事は「気合と注意で正しく動かす」ことではなく、「構造的に間違いが起きないようにする」こと。
