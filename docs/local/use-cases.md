# Repo Notes アプリ ユースケース一覧

ペルソナモデルとユーザー行動シナリオを起点に、タスクを洗い出し、ユースケースとして整理する。

---

## 1. ペルソナモデル

`hiraaaken/base` を Zettelkasten として運用する個人ナレッジワーカー。

| 項目 | 内容 |
|------|------|
| 役割 | 個人開発者・ナレッジワーカー（1 人ユーザー） |
| ゴール | 思考・読書・調査メモをモバイルで即時キャプチャし、PC でのレビュー・整理ループを維持する |
| 現在の課題 | Notion 併用で二重管理が発生。モバイルから `hiraaaken/base` へ直接書けない |
| 利用端末 | Android スマートフォン（主）、PC（Zettelkasten 編集・Claude Code） |
| ネットワーク環境 | 自宅 WiFi（安定）、移動中はモバイル回線または圏外 |

---

## 2. ユーザー行動シナリオ

### S-01: 朝のレビューシナリオ

起床後、アプリを開く。起動時 fetch が走り、昨夜の `/schedule` バッチが処理したノートが自動取得される。ノートタブで新しい literature / permanent ノートを確認し、今日の学習テーマを把握する。

### S-02: 移動中のメモキャプチャシナリオ

電車・カフェ等で思いついたアイデア、読書中の気づき、あとで調べたい事項をメモタブの FAB から即入力する。genre を選び、タグを頻度順チップから選択して保存する。オンラインであれば即座に `daily.md` へ append commit される。

### S-03: オフライン時のメモシナリオ

地下鉄や機内など圏外でも S-02 と同じ操作でメモを書く。アプリはローカルキューに積み、メモカードに「同期中」バッジを表示する。WiFi 復帰後、バックグラウンドで自動リトライされ、バッジが消える。

### S-04: 同期トラブルシナリオ

「ノートが古い気がする」「PAT 期限切れかも」と感じたとき、設定タブを開いて最終 sync 時刻とエラー文を確認する。PAT 期限切れが原因なら新しい fine-grained PAT を入力し、手動 sync ボタンで即座に回復する。

### S-05: 初期セットアップシナリオ

アプリ初回起動後、設定タブで `hiraaaken/base` の Contents R/W 権限を持つ fine-grained PAT を入力する。入力後、初期 fetch が走りノートが端末に取り込まれる。

## 4. 概念オブジェクト

このアプリで扱う主要な概念オブジェクトを整理する。

| オブジェクト | 説明 | ソース・オブ・トゥルース |
|------------|------|----------------------|
| **Note（ノート）** | `hiraaaken/base` リポジトリ内の Markdown ファイル。kind（fleeting / literature / permanent / research）・タグ・本文を持つ | GitHub リポジトリ（ローカル DB はキャッシュ） |
| **Memo（メモ）** | ユーザーがアプリから書く短文メモ。genre・tags・created・本文を持ち、`daily.md` に append される | ローカル端末（`memo_queue` → GitHub へ送信） |
| **Tag（タグ）** | ノートとメモの両方に付くトピックラベル。大小文字は保持。出現頻度でソートされ chip 表示される | GitHub リポジトリ（`tags` テーブルは派生） |
| **Genre（ジャンル）** | メモの意図分類。`idea` / `reading` / `investigate` の 3 値 enum。`/schedule` バッチへのヒント | アプリ定義（固定 enum） |
| **SyncState（同期状態）** | 同期状態を表す概念オブジェクト。最終 fetch のコミット SHA・時刻・エラー文を保持し、設定タブに表示される。DB テーブル名は `sync_state` で、本書では概念名を `SyncState` に統一する | ローカル端末（`sync_state` テーブル） |
| **MemoQueue（送信キュー）** | 未送信・失敗メモの待機リスト。オフライン時に積まれ、復帰後に flush される。`dedup_key` で重複防止 | ローカル端末（`memo_queue` テーブル） |
| **PAT（Personal Access Token）** | GitHub fine-grained PAT。`hiraaaken/base` の Contents R/W のみ許可。OS Keystore に暗号化保存される | ローカル端末（flutter_secure_storage） |

## 7. 概念設計フェーズ

*『モデルベースUIデザイン』(丸怜里, 2025) の方法論に基づく概念設計。*  
*ユースケース・タスクから概念オブジェクトを導出し、コンテンツ構造とレイアウト示唆へ展開する。*

---

### 7-1. 概念オブジェクト定義表

ユースケース・タスク・行動シナリオから **CRUD の対象になる「もの」（名詞）** を抽出し、ユーザー視点の概念オブジェクトとして定義する。技術的キャッシュ実装（DB テーブル等）は除外する。

| オブジェクト名 | 説明（サービス文脈での意味） | 出現するユースケース | CRUD 操作 | 重要度 |
|-------------|--------------------------|-------------------|----------|--------|
| **ノート** (Note) | Zettelkasten ナレッジベースの知識単位。`hiraaaken/base` リポジトリの Markdown ファイルをローカルにキャッシュしたもの。kind（fleeting / literature / permanent / research）で分類される | UC-A1, A2, A3, A4, A5, A6, A7 | **R**（閲覧・検索） ※アプリから C/U/D はしない | High |
| **メモ** (Memo) | ユーザーがモバイルで素早く書き留める一時キャプチャ。`daily.md` に append され、`/schedule` バッチ処理後にノートへ昇格する。送信前はローカルキューに存在する | UC-B1, UC-B2, UC-B3, UC-B4 | **C**（書く）/ **R**（カード一覧）/ **U**（リトライ・再送）/ **D**（送信成功後にキューから削除） | High |
| **タグ** (Tag) | ノート・メモ両方に付くトピック分類ラベル。ノートはリポジトリの frontmatter から取得。メモはユーザーが入力。出現頻度順で chip 表示 | UC-A2, UC-B1, UC-B2 | **C**（メモ入力時に新規作成）/ **R**（chip 表示・フィルタ選択）/ **U**（出現回数の更新）/ **D**（sync 時に再構築） | High |
| **同期状態** (SyncStatus) | 最終 fetch 時刻・sync 結果（success / failure）・エラー文を 1 件保持するシングルトン。サイレント失敗防止のため設定タブに常時表示 | UC-C2, UC-B4, UC-B5 | **R**（設定画面で確認）/ **U**（sync 完了時にシステムが更新） | Medium |
| **PAT（認証情報）** | GitHub fine-grained Personal Access Token。`hiraaaken/base` の Contents R/W に限定。OS Keystore に保管。UI 上はユーザーに「設定済み / 未設定」状態のみ見える | UC-C1 | **C**（初回設定）/ **R**（内部参照のみ、ユーザーには非表示）/ **U**（更新・ローテーション）/ **D**（クリア） | Medium |

### 7-2. オブジェクト間関連性表

| オブジェクト A | 関連の種類 | オブジェクト B | 多重度（A → B） | 説明 |
|-------------|----------|-------------|--------------|------|
| ノート | has-many | タグ | **0..n** | 1 つのノートは 0 個以上のタグを持つ（タグなし許容） |
| タグ | belongs-to-many | ノート | **0..n** | 1 つのタグは 0 個以上のノートに付く（タグ単独では存在しない） |
| ノート | refers-to | ノート（関連） | **0..n** | `related` フィールドで他ノートを参照（P2 wikilink 遷移） |
| メモ | has-many | タグ | **0..n** | 1 つのメモは 0 個以上のタグを持つ（`tags: []` 許容） |
| タグ | belongs-to-many | メモ | **0..n** | 1 つのタグは 0 個以上のメモに付く |
| 同期状態 | produces | ノート | **0..n** | sync 完了によって 0 個以上のノートがローカルに反映される |
| 同期状態 | flushes | メモ | **0..n** | sync 成功によって 0 個以上の pending メモがキューから削除される |
| PAT | enables | 同期状態 | **1..1** | PAT がなければ sync は一切実行できない（必須依存） |

**多重度からレイアウトパターンを推定:**

- ノート → タグ（0..n）: `tags: []` のノートが存在しうる → **タグ chip エリアの空状態設計必要**
- タグ → ノート（0..n）: タグを選んでもヒット 0 件がありうる → **フィルタ結果の空状態設計必要**
- メモ → タグ（0..n）: タグなしメモ許容 → **chip エリアの空状態設計必要**
- 同期状態 → ノート / メモ（0..n）: 初回起動直後は 0 件 → **ノートタブ・メモタブ双方の空状態設計必要**
- PAT → 同期状態（1..1）: PAT が存在しない場合は sync 不可 → **PAT 未設定時の専用空状態（誘導 CTA）設計必要**

---

### 7-3. レイアウト示唆（多重度別）

| 多重度パターン | 出現する関連 | 示唆されるレイアウト | 空状態設計 |
|-------------|------------|------------------|----------|
| **1..1**（1 対 1） | PAT → 同期状態 | Detail（シングルトン表示） | 不要 |
| **0..1**（0 または 1） | 同期状態 → 最終 sync 時刻（未 sync 時 null） | プレースホルダー付き表示 | **必要**「まだ同期していません」 |
| **0..n**（0 以上） | ノート → タグ、メモ → タグ、タグ → ノート、タグ → メモ、ノート → 関連ノート | chip リスト / カードリスト / セグメントリスト | **必要**（各関連ごとに個別の空状態文言を設計） |

### 7-4. メインオブジェクト選定

**メインオブジェクト: ノート (Note)**

**選定根拠:**  
全ユースケース 15 件のうち 7 件（UC-A1〜A7）がノートの閲覧・検索・分析を中心に組み立てられており、アプリの価値提案の核「Zettelkasten ナレッジへのモバイルアクセス」そのものがノートを指す。メモはノートへの「書き込み口」にすぎず、`/schedule` バッチ処理後にノートへ昇格する一時状態である。グローバルナビゲーションの先頭タブ・セグメント切替・タグフィルタ・wikilink 遷移・エージェント横断分析はすべてノートを軸として設計される。

**副次的オブジェクトの位置付け:**

| オブジェクト | メインとの関係 | 備考 |
|------------|-------------|------|
| メモ | ノートの前駆体（インプットキュー） | `daily.md` → `/schedule` → ノートへ昇格 |
| タグ | ノートのナビゲーション軸 | ノート・メモ双方を横断するクロスカッティング概念 |
| 同期状態 | ノート取得の健全性インジケーター | ノートが「最新か否か」を保証するメタ情報 |
| PAT | ノート取得・メモ送信のゲートキーパー | 設定タブに閉じた存在。UI 上の前提条件 |

### 7-5. コンテンツ構造図

```
ノート（メインオブジェクト）
├── 種別 kind（1..1） ── fleeting / literature / permanent / research
│   └── → セグメント chip で切り替え（タブ A 上部）
├── タグ（0..n） ── トピック分類ラベル
│   └── → chip 一覧。空状態あり（「タグなし」）
├── 本文 raw（1..1） ── Markdown 全文
│   └── → 詳細画面で markdown_widget レンダリング
└── 関連ノート（0..n） ── related フィールドのリンク先（P2）
    └── → リスト表示。空状態あり（「関連ノートなし」）

メモ（入力オブジェクト ── daily.md append の単位）
├── ジャンル genre（1..1） ── idea / reading / investigate
│   └── → ラジオボタングループ（必須選択）
├── タグ（0..n） ── トピック分類
│   └── → chip 入力 + オートコンプリート。空状態あり（tags: []）
├── 送信状態 status（1..1） ── pending / syncing / failed / sent
│   └── → pending / failed 時のみバッジ表示
└── 本文 body（1..1） ── テキスト
    └── → カード本文に表示

タグ（クロスカッティングオブジェクト）
├── → ノート（0..n）：タブ A のフィルタ chip
└── → メモ（0..n）：メモカードの chip 表示

同期状態（シングルトン ── 設定タブ）
├── 最終 sync 時刻（0..1） ── 未 sync 時は null → 空状態設計必要
├── sync 結果（0..1） ── success / failure → アイコン + テキスト
└── エラー文（0..1） ── failure 時のみ表示

PAT（シングルトン ── 設定タブ）
└── 設定状態（1..1） ── 設定済み / 未設定 → 未設定時に入力フォームを表示
```

---

### 7-6. 設計上の注意点

**空状態設計が必要な箇所（一覧）:**

| 画面・場所 | 空状態の発生条件 | 表示すべきもの |
|----------|---------------|-------------|
| ノートタブ（一覧） | PAT 未設定、1 度も sync していない | 「設定タブから PAT を設定してください」＋設定タブへの CTA |
| ノートタブ（一覧） | PAT 設定済みだがノートが 0 件 | 「ノートがまだありません」 |
| ノートタブ（タグフィルタ後） | 選択タグに該当ノートが 0 件 | 「このタグのノートはありません」 |
| メモタブ（カードリスト） | 今日のメモが 0 件 | 「メモがありません。FAB から書き始めましょう」 |
| ノート詳細（関連ノートセクション） | related が空（P2） | セクション自体を非表示 |
| 設定タブ（同期状態） | 初回起動直後、1 度も sync していない | 「まだ同期していません」 |

**複雑性が高い関連:**

- **タグ ↔ ノート（0..n ↔ 0..n）の多対多**: タグフィルタ + 種別セグメントの組み合わせクエリが必要。`note_tags` JOIN + WHERE でカバー可能だが、フィルタ条件が増えるほど SQL が複雑化する。Phase 1 は「タグ 1 件 + 種別 1 種」の複合条件に限定することを推奨。
- **メモの送信状態遷移 ↔ 同期状態**: `memo_queue.status` の `pending → syncing → sent / failed` 遷移が、メモカード UI にリアルタイム反映される必要がある。drift の `watch` + Riverpod `StreamProvider` が正しく繋がっていないと「保存したのに表示されない」体験が発生する。

**実装リスク:**

- **空状態 × PAT 未設定の衝突**: 初回起動時、ノートタブとメモタブは双方「データなし」になるが、理由が「PAT 未設定」なのか「sync 未完了」なのかによって誘導 CTA が異なる。`sync_state` と `flutter_secure_storage` の PAT 存在チェックを組み合わせて条件分岐すること。
- **タグの出現回数キャッシュ（`tags.count`）の不整合**: sync 完了後に再計算する設計だが、更新漏れが発生すると chip の並び順が古いまま固定される。sync トランザクション内で delete-insert と同時に必ず再計算すること。
